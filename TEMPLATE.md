## Design

- `railway-start.sh` (root): seeds the storage volume from the image's storage skeleton (`cp -an`, data never overwritten), creates the Laravel folders, chowns to www-data; validates `APP_KEY` (not 32 chars → stable sha256-derived 32-char key + warning), `STATIC_CRON_TOKEN` (warning), owner email (bad → admin@example.com), owner password 16–128 (bad → lock mode); hands the password over in a 0600 file that `firefly-owner.php` deletes; `exec setpriv` to www-data → `docker-php-serversideup-entrypoint /init`.
- Order inside the image: `/etc/entrypoint.d/11-execute-things.sh` (Firefly's migrations/upgrade) → `12-railway-owner.sh` (ours) → `/init` (nginx + PHP-FPM). STANDARD 8.37: the owner exists before nginx serves; single-user mode closes registration.
- `firefly-owner.php`: no users → `User::create` + `NewUserRegistered` event (same as the registration page: owner role, administration, exchange rates), with fallbacks for role/administration. Users exist → re-applies the password to the owner email if it differs (Hash::check). If no user exists after an error → exit 1 (fail closed).
- Whole `storage` on the volume (not just `storage/upload` as upstream) so the OAuth keys generated by the image survive redeploys and API tokens keep working.
- Logs to stdout (`LOG_CHANNEL=stdout`), sessions/cache in Redis.

## Improvements over market templates

- `-7wtOV` (149 deploys): unpinned images, MySQL 9 without healthcheck, `APP_KEY=${{secret()}}` of unknown length, no cron, registration open to the first visitor. `firefly-iii` and `fireflyiii`: `latest` tags, `chmod 777` workarounds or s6 juggling in start commands, open registration. This one: pinned images, owner created before the port opens, DB-backed healthcheck, daily cron as a Railway cron job, Redis sessions/cache, persistent OAuth keys, 8.29-safe variable handling.
